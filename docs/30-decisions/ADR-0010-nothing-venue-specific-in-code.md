# ADR-0010 · Ничего специфичного для заведения в коде

## Контекст
Цель владельца — довести приложение на «Мята | Platinum 4YOU» и продавать другим
заведениям. Аудит 05.09.2026 (`docs/20-architecture/customization.md`) прошёл по
всему `src/`, `netlify/` и `supabase/migrations/` и нашёл несколько сотен мест,
где в коде зашиты значения конкретного заведения: бренд и юрлицо, отделы, типы
оплат, банки Казахстана, пороги, ставка эквайринга, валюта, русский язык,
фамилии арендодателя, бухгалтера и учредителей.

Опаснее констант оказались два других класса:
- сравнения по строкам (`d.name === 'Кухня'`, `roleName === 'Админ'`) — ломаются
  молча, без ошибки, цифры уезжают не туда;
- `CHECK`-ограничения в миграциях — клиент не заведёт свой отдел без миграции базы.

## Варианты
1. Оставить как есть, под каждого клиента держать форк — плюсы: ничего не надо
   делать сейчас; минусы: каждый клиент требует правок в расчётах, ошибки
   расходятся по копиям, продажа перестаёт масштабироваться.
2. Всё подряд вынести на экран «Настройки» — плюсы: одно место; минусы: экран на
   двести значений не используется, а справочники и стартовые данные по своей
   природе не настройки.
3. Разложить по четырём адресатам в зависимости от природы значения.

## Решение
Вариант 3. Значение, которое меняется от клиента к клиенту, не пишется в код, а
попадает по адресу:

| Адресат | Что туда идёт |
|---|---|
| Настройки (`settings` + экран) | одиночные значения заведения: пороги, ставки, час отсечки, валюта, часовой пояс, график ЗП |
| Справочники (таблицы + экраны) | списки: отделы, типы оплат, категории, счета, роли, статьи |
| Стартовые данные клиента (seed) | наполнение при заведении: правила категоризации, структура P&L и Cash Flow, план счетов, бренд |
| Локализация (файлы перевода) | подписи, месяцы, форматы чисел и дат, символ валюты |

Правила для нового кода:
- Смысл не определяется сравнением с отображаемым названием. Отделы, роли, статьи
  и строки форм сопоставляются по коду или идентификатору, а не по русской строке.
- Признак поведения — колонка в базе, а не совпадение имени: суперправа —
  `is_superuser`, а не `name === 'Админ'`.
- Списки допустимых значений — справочная таблица, а не `CHECK` в миграции.
- Деньги выводятся одной функцией форматирования; символ валюты в шаблон не пишется.
- Названия заведения, юрлица и бренда в исходниках не встречаются.
- Персональные данные (фамилии контрагентов и сотрудников) в коде не хранятся.

Значения, одинаковые для всех клиентов, остаются в коде: макет PDF в миллиметрах,
номер ISO-недели, размеры страниц списков, лимиты PostgREST.

## Последствия
- Появляется общий реестр настроек: писать на каждую настройку свою обвязку из
  кеша, загрузки и сохранения (как в `dates.js:19-49`) на десятках значений не
  масштабируется.
- Часть работы уже сделана: движок правил категоризации из базы (`bank_rules`)
  применяется раньше встроенных, справочники персонала, поставщиков, счетов и
  ролей уже в базе.
- Разбор накопленного — восемь задач, TASK-015…022. Три первые (тихие поломки,
  неработающие чекбоксы уведомлений, сведение дублей) чинят то, что неверно
  работает уже сейчас, и не ждут SaaS.
- Тесты, где зашиты фамилии и названия «Мяты», переезжают на нейтральные фикстуры.
