# ADR-0012 · Свой сервер, свой API — уход с Supabase и Netlify

## Контекст
Честная оценка архитектуры 05.09.2026 (`docs/20-architecture/overview.md`): приложение —
толстый клиент над базой с REST-фасадом. Сервера приложения нет: вся логика,
проверка прав и вход исполняются в браузере, RLS открыт, anon-ключ и токены лежат
в бандле, фоновых задач быть не может, `tenant_id` нет ни в одной таблице. Для
одного заведения с доверенными пользователями это было приемлемо (ADR-0001);
для продажи другим заведениям — нет: клиент не может доверять, что его данные
видит только он, а мы — что клиент не обошёл правила.

Владелец решил не оставаться на Supabase: если поднимать свой сервер, свою
аутентификацию и свой API, от Supabase остаётся управляемый Postgres, который на
VPS есть напрямую. Хостинг в Алматы дополнительно упрощает вопрос персональных
данных сотрудников и учредителей.

## Варианты
1. Остаться на Supabase всерьёз: Supabase Auth, настоящий RLS, Edge Functions,
   `pg_cron` — минимальная переделка; сложные правила пришлось бы дублировать в SQL.
2. Мост: PostgREST внутри, за Node-сервисом с JWT и RLS; страницы почти не
   меняются; ручные endpoint'ы только для записей с правилами — недели.
3. Полное переписывание: фронтенд ходит только в наш API, PostgREST нет;
   каждый вызов `supabase.from` становится endpoint'ом — месяцы.

## Решение
Вариант 3, по решению владельца 05.09.2026, с четырьмя уточнениями:

- **Одна база, `tenant_id` в каждой таблице, RLS по арендатору.** Изоляция
  покрывается тестами: ошибка в RLS — утечка между клиентами.
- **Интерфейс на том же VPS через nginx.** Один домен: сессии в cookie без CORS.
  Netlify уходит вместе с Supabase.
- **Эксплуатация минимальная и повторяемая:** всё как файлы в `ops/`; ежедневный
  `pg_dump` в отдельное хранилище, автообновления безопасности, проверка
  доступности с уведомлением в Telegram, восстановление из бэкапа проверяется
  раз в месяц.
- **Расчёты не переписываются.** `src/lib` — чистый JavaScript без браузерных
  зависимостей (ADR-0009); на сервере он исполняется как есть.

Порядок, от самого опасного:
0. Сервер: Postgres 16, nginx с TLS, бэкапы, мониторинг (`ops/`).
1. Перенос данных `pg_dump` → VPS; из миграций уходят `GRANT … TO anon` и открытые политики.
2. Node-сервис: вход с хешированием паролей, сессии, `tenant_id` + RLS.
   **До этого пункта второго клиента подключать нельзя.**
3. Секреты и интеграции в сервис: Telegram, iiko.
4. Записи с правилами через API: отчёт смены, импорт выписки.
5. Endpoint'ы чтения вместо каждого `supabase.from`; фронтенд перестаёт знать о базе.
6. Планировщик: ночная синхронизация iiko, напоминания.

## Последствия
- Заменяет ADR-0008 (self-hosted Supabase на VPS) целиком и уточняет ADR-0001:
  «SPA без бэкенда» перестаёт быть верным после пункта 2.
- Правило 9 (`fetchAll` против лимита 1000 строк PostgREST) отмирает вместе с
  PostgREST; до пункта 5 действует.
- Миграции применяются `psql` через SSH, а не через Supabase; доступ к серверу
  у ассистента только через настроенный ключ на машине владельца.
- Задачи: TASK-030…036, в `tasks/BACKLOG.md`. Работа над функциями, трогающими
  доступ к данным, замораживается до пункта 5; чистая логика в `src/lib` — нет.
