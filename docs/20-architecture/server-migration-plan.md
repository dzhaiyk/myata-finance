# План переезда на свой сервер и свой API

Решение — ADR-0012 (05.09.2026). Этот документ — рабочий план, к которому
возвращаемся, когда куплен сервер. До тех пор приложение живёт на Supabase и
Netlify, правится и выкатывается как обычно: переезд — отдельная линия, не
заморозка.

## Куда идём

```
Браузер (SPA, тонкий)  ──cookie-сессия──▶  nginx  ──▶  Node-сервис (API)  ──▶  PostgreSQL 16
                                              │              │  src/lib — расчёты
                                              └──статика     └──интеграции, планировщик
                                                    всё на одном VPS в Алматы
```

- Одна база, `tenant_id` в каждой таблице, RLS по арендатору — проверяется тестами.
- Фронтенд не знает о базе: только наш API. Правила исполняются на сервере.
- Расчёты (`src/lib`) не переписываются — чистый JavaScript, работает в Node как есть.
- Supabase и Netlify уходят целиком.

## Объём (снято 05.09.2026)

163 обращения к базе из фронтенда по 24 таблицам. Самые тяжёлые:
`account_transactions` 21, `bank_transactions` 20, `daily_reports` 15, `accounts` 12,
`settings` 10, `pnl_data` 10. Это объём шага 5 — примерно 24 ресурса, каждый
с чтением и записью, правами и тестом. Оценка честная: месяцы, не недели.

## Что собрать перед стартом (прерогатива владельца)

- Сервер на vs.kz: Ubuntu 24.04 LTS, 2 vCPU / 4 ГБ / 40 ГБ NVMe достаточно.
- Домен приложения — для TLS и nginx.
- Место под бэкапы вне сервера: объектное хранилище или второй сервер.
- Модель доступа: SSH-ключ с машины владельца (ассистент запускает `ops/` сам)
  или владелец запускает скрипты и присылает вывод. Пароли и ключи ассистент
  не принимает.

## Шаги и ворота

| Шаг | Задача | Что делаем | Ворота — не идём дальше, пока |
|---|---|---|---|
| 0 | TASK-030 | `ops/`: Postgres 16, nginx с TLS, ежедневный `pg_dump` во внешнее хранилище, автообновления, проверка доступности → Telegram | восстановление из бэкапа проверено вручную |
| 1 | TASK-031 | `pg_dump` из Supabase → VPS; из миграций 001–030 убрать `GRANT … TO anon` и открытые политики | контрольные суммы таблиц совпали |
| 2 | TASK-032 | Node-сервис: вход с хешированием, сессии в cookie, `tenant_id` везде, RLS по арендатору | тесты RLS: клиент A не видит клиента B. **До этого второго клиента не подключать** |
| 3 | TASK-033 | Telegram и iiko в сервис; `VITE_`-токены уходят из бандла | в бандле нет ни одного секрета |
| 4 | TASK-034 | Отчёт смены и импорт выписки — через API, правила на сервере (BR-SHF-020 и др.) | подправленный клиент не может записать несходящуюся кассу |
| 5 | TASK-035 | Endpoint'ы чтения вместо каждого `supabase.from`; `fetchAll` и правило 9 отмирают | в `src/` нет `supabase.from` |
| 6 | TASK-036 | Планировщик: ночной iiko, «отчёт не сдан», еженедельный food cost | уведомления, что были фикцией, работают |

Порядок — от самой опасной дыры к менее опасным. Шаги 3, 4, 5 после шага 2
можно вести параллельно.

## Что переезжает без изменений и почему это важно

Правило 10 и ADR-0009 держали расчёты в чистых функциях: `pnlCompute`,
`cashflowCompute`, `reconcile`, `bankImport`, `categorize`, `config`. Ни одна не
зависит от браузера. Сервер получает готовый «engine» — переписывается слой
доступа к данным, не логика. Справочники и структуры отчётов (ADR-0011) уже в
базе — сервер получит данные, а не константы.

## Что делать до переезда, чтобы не увеличивать долг

- Новые расчёты — только в `src/lib` (правило 10).
- Новые обращения к базе не размазывать по страницам: собирать в `src/lib/*.js`
  рядом с существующими (`departments.js`, `branding.js`) — эти файлы станут
  клиентами API одним движением.
- Значения заведения — в базу, не в код (ADR-0010): сервер не должен их знать.
