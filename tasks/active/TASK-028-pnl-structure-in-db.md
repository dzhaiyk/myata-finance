## Цель — что станет возможным
Строки P&L — их порядок, подписи, вложенность и привязка статей — живут в базе и
правятся из «Справочников». `PNL_STRUCTURE` из кода становится стартовыми данными
клиента. Формулы остаются в `pnlCompute`.

## Не входит (out of scope)
- Новые формулы из интерфейса: расчётная строка добавляется только кодом.
- Cash Flow — TASK-029 (сначала вынос расчёта в `src/lib`, вопрос reporting #1).
- Дашборд и аналитика продолжают читать значения по ключам строк — ключи не меняются.

## План
1. Миграция 029: таблица `pnl_lines` — `key` (неизменяемый), `label`, `level`,
   `section`, `kind` (`category` | `calc` | `group`), `category_code` → `categories`,
   `daily_field`, `department`, `label_prefix`, `sort_order`, `is_active`.
   Seed — все 90 строк из `PNL_STRUCTURE` один в один.
2. `src/lib/pnlStructure.js`: загрузка при старте (как справочники), кеш,
   `getPnlStructure()`; `pnlCompute` берёт строки оттуда, формулы — по `key`
   из `CALC_FORMULAS` в коде. Пока база не загружена — статичная константа.
3. Тест эквивалентности: на одних данных структура из seed и из константы дают
   одинаковые `computeMonthValues` — ключ за ключом. Без этого теста этап не
   закрывается.
4. Вкладка «P&L» в «Справочниках»: переименовать, переставить, скрыть, привязать
   статью к строке, добавить строку-статью. Расчётная строка — подпись и порядок,
   без формулы.
5. `PNL_STRUCTURE` остаётся в коде как seed нового клиента и запасной вариант;
   `CATEGORIES` из `categorize.js` уходит (TASK-026 закрывается здесь).
6. Документы: data-model, reporting/rules, customization; `pnl-structure` skill.

## Критерии приёмки — проверяемые, по одному на строку
- P&L за любой месяц 2026 совпадает до тенге с тем, что было до задачи.
- Переименование строки в «Справочниках» видно в P&L, цифры не меняются.
- Скрытая строка не показывается, но её значение по-прежнему входит в итоги.
- Новая строка-статья с привязанной статьёй появляется в P&L с суммой по ней.
- `npm test` и `npm run build` зелёные.
